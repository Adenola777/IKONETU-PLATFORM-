# Database access tests

These scripts check the row level security rules in `supabase/migrations` on a plain Postgres 16 server.

1. `00_supabase_stubs.sql` creates the small parts of Supabase that the migrations expect: the `auth` schema with `auth.uid()` and `auth.role()` and an `auth.users` table with `email` and `last_sign_in_at`, which read the claims both ways Supabase's own functions do, the `anon` and `authenticated` roles, and the `storage` schema. It also sets the default privileges a real Supabase project has, which give `anon` and `authenticated` every right on each new table, view and function in `public`.
2. Apply the migration files in order.
3. `01_rls_checks.sql` runs 25 checks, as signed-in users and as a visitor who is not signed in. Each check prints what it expects, for example "expect RLS error" or "expect 0 rows".
4. `02_investor_checks.sql` runs 77 checks of the investor side: sign-up as a pending investor, an admin's approval, publishing, discovery, the evidence an investor may see, introductions, conversations, staff decisions and recorded scores. It makes its own people, and each check prints PASS or FAIL with what it found, so a run is read by counting the FAIL lines.

Example:

```sh
createdb ikonetu_test
psql -d ikonetu_test -f supabase/tests/00_supabase_stubs.sql
psql -d ikonetu_test -f supabase/migrations/20261005000001_core.sql
psql -d ikonetu_test -f supabase/migrations/20261005000002_rubric_v2.sql
psql -d ikonetu_test -f supabase/migrations/20261005000003_lock_public_profiles.sql
psql -d ikonetu_test -f supabase/migrations/20261015000001_investor_interest.sql
psql -d ikonetu_test -f supabase/migrations/20261015000002_investor_side.sql
psql -d ikonetu_test -f supabase/migrations/20261015000003_venture_ask.sql
psql -d ikonetu_test -f supabase/migrations/20261015000004_resilience.sql
psql -d ikonetu_test -f supabase/migrations/20261017000001_admin.sql
psql -d ikonetu_test -f supabase/migrations/20261020000001_score_v3.sql
psql -d ikonetu_test -f supabase/migrations/20261020000002_rubric_v3.sql
psql -d ikonetu_test -f supabase/tests/01_rls_checks.sql
psql -d ikonetu_test -f supabase/tests/02_investor_checks.sql 2>&1 | grep -c FAIL   # 0 when every check passes
psql -d ikonetu_test -f supabase/tests/03_resilience_checks.sql 2>&1 | grep -c FAIL # 0 when every check passes
psql -d ikonetu_test -f supabase/tests/04_admin_checks.sql 2>&1 | grep -c FAIL      # 0 when every check passes
psql -d ikonetu_test -f supabase/tests/05_score_checks.sql 2>&1 | grep -c FAIL      # 0 when every check passes
psql -d ikonetu_test -f supabase/tests/06_register_checks.sql 2>&1 | grep -c FAIL   # 0 when every check passes
sh supabase/tests/race_introductions.sh -d ikonetu_test                            # prints PASS or FAIL
```

All 23 checks gave the expected result on 5 October 2026. Checks 16 to 23 were added the same day, after Supabase's advisor found that `public_profiles` could be read, changed and emptied by a visitor who is not signed in; without migration 0003, checks 16, 17, 18 and 19 fail. Run them again after any change to a policy.

Checks T8b and T8c were added on 15 October 2026 with the `investor_interest` table. They check that a signed-in user can neither read nor write it. All 25 checks gave the expected result that day on a local PostgreSQL 16, with the four migrations applied in order.

Migration 20261015000002 was added on 15 October 2026. With all five migrations applied on a local PostgreSQL 16 that day, the 25 checks in `01_rls_checks.sql` gave the expected result and the 75 checks in `02_investor_checks.sql` passed. Two checks in the first file changed with it: a second founder can no longer see another founder's venture (T12) or founder card (T20), because a venture is now visible only to approved investors, and only once its founder publishes it.

Migration 20261015000003 adds the founder's ask, and checks I6a and I26a cover it. With all six migrations applied on a local PostgreSQL 16 on 15 October 2026, the 77 checks in `02_investor_checks.sql` passed.

Migration 20261015000004 adds the checks in `03_resilience_checks.sql` and `race_introductions.sh`. The 13 checks cover evidence and its files saved in one transaction, a founder removing only an unrecorded file of their own, a form sent twice kept once, who may call `health()`, `submit_evidence()` and `ventures_with_stale_scores()`, and the daily limit on introduction requests. `race_introductions.sh` sends two requests at the same moment from two sessions. Without the migration they made eleven requests out of a limit of ten; with it they leave ten. All of it passed on a local PostgreSQL 16 on 15 October 2026, with the seven migrations applied in order, and the 77 checks in `02_investor_checks.sql` still passed.

Migration 20261017000001 adds the checks in `04_admin_checks.sql`. The 43 checks cover who may read the overview, the founders list and the accounts list; the north star count; hiding a profile with a reason, the founder reading it and being unable to publish or lift it, and lifting it; a venture created already published without a pitch; role changes, including that nobody changes their own role and that a founder made staff leaves investors' view; and suspension, including that a suspended founder cannot add evidence, publish, rename the venture, answer a request or send a message, and that a suspended admin loses access. All of it passed on a local PostgreSQL 16 on 17 October 2026 with the eight migrations applied in order. The 77 checks in `02_investor_checks.sql`, the 13 in `03_resilience_checks.sql` and the race check still passed, and the output of `01_rls_checks.sql` was the same as on 15 October. On a database without this migration, a founder created a venture already published without a pitch, and a suspended founder added evidence.

Migrations 20261020000001 and 20261020000002 add the checks in `05_score_checks.sql`. The 21 checks cover rubric v3 being the only active rubric, with 175 signals, 12 categories and weights that add up to 100; a founder's own statement for a self-declared signal, and its refusal for a signal a reviewer must check, a statement under 10 characters, another founder's venture, a suspended founder, a repeated request key and a visitor; that an approved investor does not see a statement; recording a score by the server's service role and by a reviewer, and its refusal for the founder, for a reviewer's own venture and for a visitor; one monthly record per month, holding the newer total; that the record of a month that has ended cannot change; who may read the records; and that a statement whose score is not recorded yet appears on the staff list of scores to update. All 21 passed on a local PostgreSQL 16 on 20 October 2026 with the ten migrations applied in order. The 77 checks in `02_investor_checks.sql`, the 13 in `03_resilience_checks.sql`, the 43 in `04_admin_checks.sql` and the race check still passed, and the output of `01_rls_checks.sql` was the same with and without the two migrations.

Migration 20261021000001 opens IkonetU to every country and records the student founder declaration. With all twelve migrations applied on a local PostgreSQL 16 on 21 October 2026, the 77, 13, 43 and 21 checks in files 02 to 05 passed, and the output of `01_rls_checks.sql` was the same with and without it. Add the line `psql -d ikonetu_test -f supabase/migrations/20261021000001_any_country.sql` after the rubric v3 migration in the example above.

Migration 20261024000001 adds the investor register and the checks in `06_register_checks.sql`. Add the line `psql -d ikonetu_test -f supabase/migrations/20261024000001_investor_register.sql` after the any country migration in the example above. The 35 checks cover who may read and add to the register: a founder, a reviewer, an approved investor, a visitor and a suspended admin may not, and nobody reads or writes the table directly. They also cover an admin adding a list, with spaces in a name tidied; the addition's entry in the audit log; the same list added again changing nothing and writing no entry; a number already there with another name or date stopping the whole list, with nothing from it kept; dates that do not exist, are in another format or are after today; a number given twice, a number of two digits and a name of one character; an empty list and something other than a list; the months from the first to the last with an empty month listed and running totals; and the list in register number order, searched by name and by number, filtered by month and read page by page. It expects the register to start empty. All 35 passed on a local PostgreSQL 16 on 24 October 2026 with the thirteen migrations applied in order, the 77, 13, 43 and 21 checks in files 02 to 05 and the race check still passed, and the output of `01_rls_checks.sql` was the same with and without it.

Migration 20261027000001 adds the activity feed and the checks in `07_activity_checks.sql`. Add the line `psql -d ikonetu_test -f supabase/migrations/20261027000001_activity_feed.sql` after the investor register migration in the example above, and `psql -d ikonetu_test -f supabase/tests/07_activity_checks.sql 2>&1 | grep -c FAIL` after the register checks. The 35 checks cover what makes an entry: a pitch, the first publication, the ask, a new pitch video and evidence approved by a reviewer or backed by an outside source each make one, while a venture and its evidence being created, a new transcript, a second ask or pitch the same day, publishing again, a founder's own statement, an approval by the automatic check, evidence for a signal the active rubric does not hold, a request for an introduction and a declined one make none. An accepted introduction keeps the investor's type only, and no entry holds a name, a firm, a note, the ask or a summary. They also cover who reads the feed: other founders, approved investors and reviewers read it, a pending investor, a suspended founder and a visitor cannot, and nobody reads or writes the table or calls the function that writes it directly; an unpublished venture stays out, its founder and staff read it by asking for it, and an investor cannot. They cover reading page by page and since an entry, a profile an admin hides or a founder suspended leaving the feed and coming back when published again, and the count of active weeks in discovery and in the staff founders list. Because founders no longer post updates, I0 in `02_investor_checks.sql`, R4 in `03_resilience_checks.sql` and X34 check that a founder cannot post one, and S8 in `04_admin_checks.sql` writes the venture's description instead. All of it passed on a local PostgreSQL 16 on 27 October 2026 with the thirteen migration files applied in order, both on its own and after files 01 to 06: 78, 13, 43, 21, 35 and 35 checks in files 02 to 07, the race check, and the output of `01_rls_checks.sql` the same with and without the migration.

Migration 20261027000002 adds the admin records and the checks in `08_admin_records_checks.sql`. Add the line `psql -d ikonetu_test -f supabase/migrations/20261027000002_admin_records.sql` after the activity feed migration in the example above, and `psql -d ikonetu_test -f supabase/tests/08_admin_records_checks.sql 2>&1 | grep -c FAIL` after the activity checks. `00_supabase_stubs.sql` now gives `auth.users` the `created_at` and `email_confirmed_at` columns, which the unfinished sign-ups read. The 130 checks cover who may read and change the founder register, its responses, the introductions from the registers, the pitch video files, the reports and the settings: a founder, an investor, a reviewer where the page is an admin's, a visitor and a suspended admin may not, and nobody reads or writes the tables directly. They also cover the sample rows being left out of every count; a record's responses with the name each one gave; deleting a record and removing an unfinished sign-up; linking a register entry to an investor's account and unlinking it; an introduction's status and its history; a video approved only with all four checks and rejected only with one of six reasons, and a video linked to a founder record carrying that record's startup, founder and sector; one open report per person on each conversation and its resolution; the pitch rules, the introduction rules and the mode, their ranges, the audit log they write, and the pitch and introduction triggers holding founders and investors to them; the staff list, adding and removing staff, and nobody removing themselves; the dashboard's figures, the analytics source with each founder's grouped country and no name, the register's history, and the database page counting every table, naming the latest migration Supabase recorded and reading no value. R11 in `03_resilience_checks.sql` now looks for the limit as the new trigger words it, "the limit of 10 requests a day". All of it passed on a local PostgreSQL 16 on 27 October 2026 with the fourteen migration files applied in order.
